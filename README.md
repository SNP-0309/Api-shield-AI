# API Shield

API Shield is a behavior-aware API gateway. It evaluates live requests before forwarding them to an upstream service, stores short-lived telemetry in Redis, scores client behavior with an Isolation Forest model, and adapts each client’s request budget when risk increases.

## How it works

```text
API client
   │  X-API-Key / Authorization: Bearer ...
   ▼
API Shield gateway (/proxy/*)
   ├─ authenticate request
   ├─ read and update Redis sliding-window telemetry
   ├─ extract behavioral features
   ├─ ask the ML service for an anomaly score
   ├─ apply adaptive rate policy
   └─ forward the request to UPSTREAM_URL
          │
          ▼
       Your API
```

The dashboard reads the telemetry generated by real gateway traffic. It does not contain seeded traffic, hard-coded business responses, a traffic generator, or a state-reset action.

## Request flow

Configure an upstream API, then send requests through the gateway:

```bash
curl -i \
  -H "X-API-Key: $SENTINEL_API_KEY" \
  https://gateway.example.com/proxy/v1/customers
```

The gateway preserves the upstream status code and response body, removes gateway-only credentials before forwarding, and adds standard `RateLimit-*` and `X-Sentinel-*` response headers.

`GET /api/ping` is a small protected connectivity endpoint. It is not a replacement for your application API; use `/proxy/*` to protect the real service.

## Enforcement policy

The final risk score is normalized to `0.00–1.00`:

```text
finalRisk = 0.65 × modelScore + 0.20 × behaviorRisk + 0.15 × rateRisk
```

| Posture | Score | Per-client limit | Gateway action |
| --- | --- | ---: | --- |
| SAFE | `< 0.30` | 100 req/min | Allow |
| SUSPICIOUS | `0.30–0.59` | 50 req/min | Allow and monitor |
| HIGH_RISK | `0.60–0.79` | 15 req/min | Throttle |
| CRITICAL | `≥ 0.80` | 5 req/min | Return HTTP 429 |

Behavior is calculated from actual observations in the previous 60 seconds: request velocity, interval variance, payload sizes, endpoint repetition and entropy, response error rate, method mix, user-agent changes, and burst intensity.

## Services

- `backend`: Node.js/Express gateway, API-key authentication, proxying, adaptive enforcement, and dashboard API.
- `ml-service`: FastAPI inference service with the deployed Isolation Forest and scaler artifacts.
- `redis`: Shared sliding-window telemetry, rate-limit state, event feed, and counters.
- `frontend`: React operations dashboard backed by the `/security/*` endpoints.

## Configuration

Copy `.env.example` to `.env` and replace every placeholder with deployment values. For the dashboard build, copy `frontend/.env.example` to `frontend/.env` and use the dashboard key.

Important variables:

- `UPSTREAM_URL`: base URL for the API that receives `/proxy/*` requests.
- `REDIS_URL`: shared Redis connection string. Redis is required in production.
- `SENTINEL_API_KEYS`: comma-separated client keys accepted by `/api/*` and `/proxy/*`.
- `SENTINEL_ADMIN_API_KEY`: key accepted by the security dashboard endpoints.
- `CORS_ORIGINS`: comma-separated browser origins allowed to call the gateway.
- `TRUST_PROXY`: set to the number of trusted reverse-proxy hops when deployed behind a load balancer.
- `SECURITY_FAIL_OPEN`: leave `false` in production so an unavailable telemetry dependency does not silently bypass enforcement.
- `ALLOW_IN_MEMORY_FALLBACK`: keep `false` in production. It is only for local development without Redis.

API keys should be long random values and should normally be issued and rotated by an identity or secrets system. The dashboard key is sent to the browser by the frontend build; for a multi-user deployment, put the dashboard behind your SSO or an authenticated reverse proxy instead of treating a browser key as a secret.

## Run with Docker Compose

```bash
copy .env.example .env
# edit .env: set keys, CORS_ORIGINS, and UPSTREAM_URL
docker compose up --build
```

Open the dashboard at `http://localhost:3000`. The gateway listens on `http://localhost:5000`; the ML service and Redis are internal stack dependencies.

If the dashboard key is set in `.env`, Compose passes it as a frontend build argument. Do not use real production secrets in a publicly distributed frontend image.

## Run locally

Install dependencies once:

```bash
cd backend && npm install
cd ../frontend && npm install
cd ../ml-service && pip install -r requirements.txt
```

Start Redis, then run the three services from separate terminals:

```bash
cd ml-service
python app.py

cd backend
npm run dev

cd frontend
npm run dev
```

The convenience scripts `start-all.ps1` and `start-all.bat` start the local services. They do not create traffic; use your own API clients or application workloads.

## Model lifecycle

The production image loads the committed model artifacts from `ml-service/models`. Replace those artifacts with a model trained and validated against your organization’s baseline request feature export before deployment.

```bash
cd ml-service
python train_model.py --data path/to/traffic_baseline.csv --models-dir models
```

The training CSV must contain the 13 feature columns listed in `ml_model.py`. An `is_anomaly` column is optional and is used only for offline validation reporting; it is not required by the unsupervised training process.

## Operational endpoints

- `GET /health`: liveness check; no authentication required.
- `GET /ready`: readiness check for Redis and ML dependencies.
- `GET /api/ping`: authenticated and protected reference endpoint.
- `ANY /proxy/*`: authenticated, evaluated, and forwarded to `UPSTREAM_URL`.
- `GET /security/overview`: current aggregate telemetry.
- `GET /security/clients`: active client profiles.
- `GET /security/traffic`: recent traffic events.
- `GET /security/timeseries`: recent traffic time series.
- `GET /security/client/:id`: detailed behavioral profile and deterministic rationale.

## Production checklist

- Put the gateway behind TLS and a load balancer.
- Use a managed Redis deployment with backups, access control, and monitoring.
- Store API keys in a secrets manager and rotate them regularly.
- Restrict `CORS_ORIGINS` to the actual dashboard origin.
- Set `TRUST_PROXY` correctly for the deployment topology.
- Train and validate model artifacts on real baseline traffic.
- Add application-level authentication and authorization in the upstream service.
- Export logs and metrics to the organization’s observability platform.
- Review telemetry retention and IP/user-agent handling against privacy requirements.
